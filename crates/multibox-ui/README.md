# multibox-ui

`git multibox` 的桌面界面：一眼看清一个仓库开了哪些工作区、每个占多少磁盘、空间花在哪，并直接在界面里清理。用 [GPUI](https://www.gpui.rs)（Zed 编辑器的 GPU 加速 UI 框架）和 [GPUI Kit](https://github.com/longbridge/gpui-kit) 组件库写成。

## 运行

发布包和安装脚本会把 `multibox-ui` 和 `git-multibox` 装在同一个目录。在仓库里：

```bash
git multibox ui            # 打开当前仓库，终端马上就能接着用
git multibox ui ../other   # 或者指定仓库里的任意目录
```

也可以直接运行 `multibox-ui [<目录>]`。成功打开仓库后会自动记住，下次直接启动时恢复上次的仓库；指定目录或从另一个仓库里启动时，优先打开指定目录或当前仓库。记住的仓库已不存在时，窗口会让你重新选一个。从源码运行：

```bash
cargo run -p multibox-ui --release -- <仓库里的任意目录>
```

## 界面

三块，各回答一个问题。

**概览：一共占了多少，Multibox 省了多少，有什么能清？**

四张一样大的卡片，结构相同：标题、一个大数字、一句说明、底部一条进度条、一个按钮或一行小字。并排时每一行都对齐；窗口窄时排成两行两张。

- 占用磁盘：所有工作区在磁盘上实际占的空间，下面一条按类型分段的条。同一份数据有几个硬链接也只算一次。
- 省下的空间：用了 Multibox 少占的磁盘，下面的条把它和占用磁盘放在一起比。
- 省下的工作：带过去的缓存让多少个依赖包不用重新编译、多少个资源不用重新导入，以及估算的时间（见下文）。
- 可清理：能放心清掉的东西加起来多大，一个“清理”按钮。

工作区所在的卷还能写入多少、是什么文件系统，在顶栏右边；点它，右侧换成磁盘详情（见下文“磁盘”）。

顶栏就是窗口的标题栏，没有另一条系统标题栏压在上面：拖动顶栏的空白处移动窗口，双击最大化。Windows 上最右边是最小化、最大化和关闭，悬停在最大化上会出现系统的贴靠布局；macOS 上系统的三个按钮在顶栏左边。Linux 上仍用窗口管理器的标题栏。

**列表：有哪些工作区，各占多少，什么状态？**

列表标题行的右边是图例，概览和每一行的占用条都按它来读。每行是名字和分支、一行状态、一条占用条、独占大小。独占就是删掉它能腾出的空间；下面“+N 共用”的小字是另外的共用硬链接，数据磁盘上只存一份，删掉它也不会腾出来。所有行的条用同一个比例，长短可以直接比。状态用图标加一两个字：

| 状态 | 含义 |
| --- | --- |
| 主工作区 | 其他工作区的分支合并到这里 |
| 已锁定 | 不能删除，先解锁 |
| 编辑器开着 | 引擎的编辑器正在用它，不能删除 |
| Cindy 正在使用 | Cindy 会话仍持有这个工作区，不能删除或清理 |
| 无法确认 Cindy 占用 | 占用记录读取失败，暂时禁止删除或清理 |
| N 处未提交 | 有改动或未跟踪的文件 |
| 领先 N / 落后 N | 和主工作区的分支比，多或少几个提交 |
| 已合并，可清理 | 提交都已在主分支里，也没有改动 |
| N 天前 | 最近一次提交的时间 |

行上没有按钮。点一行选中它，操作都在右边。

**右侧：选中的这个工作区**

它的操作、独占和共用各多大（独占 + 共用 = 文件合计，条下面用括号分开标出）、按类型的明细、这个工作区省下了什么、最大的几个目录、分支和最近一次提交、识别到的工程（Unity / Rust / pnpm / TypeScript）。

**磁盘：点顶栏的磁盘标签**

右侧换成工程所在的卷，再点一次标签或右上角的叉回到工作区；点列表里的工作区也会回去。

- 能写入：卷的剩余空间。Dev Drive 是另一块盘上的一个虚拟盘文件（`git multibox setup` 建在 `<盘>\Multibox\multibox.vhdx`），写入会让文件变大、删文件不会变小，所以能写入的是卷的剩余和那块盘的剩余里较小的一个；那块盘先不够时标签变黄，这里说明原因。顶栏显示的也是这个数。
- 虚拟盘文件：路径、现在占了多少，以及它所在那块盘的剩余。
- 调整大小：不提供缩小。Windows 只能缩小 NTFS 分区，不能缩小 ReFS，而虚拟盘按需增长，调小上限也腾不出空间；要腾空间，就清理工作区或迁移留下的原工程。调大 Dev Drive 的上限这一版还不提供。macOS 上卷和同一容器里的其他卷共用空间，没有要调的。
- 迁移留下的原工程：`git multibox init` 把工程搬到 Dev Drive 时，原来的目录改名为 `<名字>.multibox-original` 留在原处，并记在新工程的 `.git/multibox-kept.json` 里。这里列出它的大小，并和现在的工程比较：分支、标签、stash 指向的提交是否都在，原目录里有改动的文件是否和现在的一样。都一致时它也算进概览的“可清理”。这一版之前迁移的工程没有记录，不会列出来。

## 占用怎么分

| 类型 | 条上的样子 | 含义 |
| --- | --- | --- |
| 共用缓存 | 蓝色斜线 | 数据还有别的名字的硬链接。NTFS 上 Multibox 让只写一次、不会再改的缓存（比如编译好的依赖库）通过硬链接在工作区之间指向同一份数据。它们不重复占空间，所以不填色、只画斜线，排在条的最前面，和后面实心的部分隔开一点：实心的那段才是这个工作区真正占着的。数据的所有名字都在同一个工作区里时（比如 Cargo 在 `target/` 里给同一个编译结果起的两个名字），数据算作这个工作区独有，只有多出来的名字算这里 |
| Git | 浅一档的蓝 | 主工作区的 `.git`，所有工作区共用 |
| 独有缓存 | 蓝色 | git 不管的其余文件，主要是编译和导入的结果（`Library/`、`target/`、`node_modules/` …），只属于这个工作区，删掉它就腾出来 |
| 源码 | 深一档的蓝 | git 跟踪的文件 |

整个界面只有这一种青金石蓝是“数据的颜色”，比常见的界面蓝更深、更沉；绿、黄、红只用来表示已合并、有改动和出了问题，并且总是带着图标和文字。条上的四段从“和别人共用”到“最属于这个工作区”排列：共用的那段是斜线，后面三段实心，是同一种蓝由浅到深（深色模式下由暗到亮）的三档，每档亮度差不多一样，所以实心部分读起来是一种颜色渐渐加深，而不是一排拼起来的色块。实心和斜线一眼就能分开，不靠颜色；相邻实心段的区分度按红绿色盲、蓝黄色盲和正常色觉核对过，都在 OKLab ×100 的 18 以上。“省下的空间”那条末尾的斜线也是同一个意思：本来要占、实际没占的部分。不到 3 像素宽的段不画，数值仍然在图例、悬停提示和明细里。

大小按系统文件管理器的算法显示，和资源管理器或访达里看到的一致：Windows 上按 1024 进位，macOS 上按 1000。

在 Dev Drive（ReFS）和 APFS 上，没改过的数据通过 reflink 共用，文件系统不提供逐个文件的共用量，界面显示的是文件大小，所以独占、占用磁盘和可清理都只是上限，数字前标着“最多”；实际占用以磁盘剩余空间为准。

## 省下的空间和时间

`git multibox add` 建好工作区后，会在它自己的 git 目录里（比如 `.git/worktrees/feature/multibox.json`）记下这次带过去了什么：多少文件和数据、其中多少通过硬链接共用、建的前后磁盘剩余空间少了多少、用了多久、带过去多少个编译好的依赖包、多少个 Unity 资源的导入结果。工作区被删除时，git 会连同这份记录一起删掉。

- 省下的空间：NTFS 上是此刻工作区之间通过硬链接共用省下的空间，从磁盘上直接量出来，是精确值；同一个工作区里自己建的硬链接不算。Dev Drive 和 macOS 上，文件系统事后说不清哪些数据是共用的，所以用创建时的记录：带过去的数据减去磁盘实际少掉的空间。
- 省下的工作：数量是精确的。依赖包按 Cargo 在 `.fingerprint/` 下给每个编译单元建的目录计数，同一个包算一次；工作区自己的包不会带过去，所以都是依赖。Unity 资源按带过去了 `Library/` 的工程里被 git 跟踪的 `.meta` 文件计数，每个资源和文件夹都有一个。
- 时间是估算：按 [benchmarks](../../docs/benchmarks.md) 里一台 32 线程 Windows 工作站的速度，Unity 每个资源约 16 毫秒（56,961 个资源导入用了 806 到 1,044 秒），Rust 每个依赖包约 0.15 秒（带过去 559 个依赖，编译少用 81 秒）。换一台机器或工程，实际可能快或慢好几倍，所以界面上总是写着“估算”。

这一版之前建的工作区没有记录：它们省下的空间照样能量出来，省下的工作不会算进去。

## 操作

| 按钮 | 做的事 |
| --- | --- |
| 新建工作区 | `git multibox add <路径> [-b <分支>]`，带进度 |
| 清理（概览） | 先列出会清掉什么，确认后一起做：已合并的工作区连同分支、中断的删除留下的 `.multibox-trash-*` 目录、目录已不存在的工作区记录（`git worktree prune`） |
| 清理（右侧） | 只清选中的这个已合并的工作区和它的分支（`git branch -d`，没合并的分支删不掉） |
| 合并并清理 | `git multibox finish`：合并进主工作区当前分支，再删工作区和分支；有冲突时停下，什么都不删 |
| 删除 | `git multibox remove`；有改动时确认框会说明，并改为连同改动一起删除 |
| 锁定 / 解锁 | `git worktree lock` / `unlock` |
| 打开文件夹 / 终端 / 复制路径 | 在文件管理器、终端里打开，或复制路径 |
| 删除（迁移留下的原工程） | 先和现在的工程比较；有没带过去的提交或改动时，确认框会列出来 |

所有会删东西的操作都先弹确认框。编辑器开着或 Cindy 会话正在使用的工作区不能删除或合并清理，也不会计入概览的可清理空间；锁定的要先解锁。执行删除前会重新读取 Cindy 的占用记录，因此确认框打开后才开始运行的会话也会受到保护，连同改动一起删除也不能绕过。请先停止会话并等待任务退出、释放占用，再刷新后清理。

Cindy 占用来自本机各个正式版、开发版及 Host 配置目录的 `worktree-runtime-leases`，同时兼容旧版共享记录，以及环境变量 `XDT_USER_DATA_DIR` / `CINDY_HOST_DATA_DIR` 指定的目录。只读取记录，不修改 Cindy 数据。记录仍存在时，即使持有者进程已退出，也可能有子进程继续使用工作区，因此交由 Cindy 释放记录后才允许清理；读取失败时同样保持保护。

窗口跟随系统的浅色和深色，也可以用右上角的按钮切换。`Ctrl+R`（macOS 上 `Cmd+R`）或 `F5` 从头重新测量。

窗口自己会跟上变化，不用一直点刷新：在前台时每 30 秒重新读一次工作区列表和每个工作区的 Git 状态（一个百万文件的仓库读一次约 0.1 秒），别的工具新建或删除的工作区、新改的文件都会出现；切回窗口时马上读一次，距上次测量超过 2 分钟的话还会按变化增量重测占用。正在测量或正在执行操作时不打扰，操作结束后本来就会刷新。这种自动刷新不会让刷新按钮转起来。

所有工作区一起测量，共用一组线程，小的先出结果。测量的时间几乎都花在逐个打开文件读硬链接数上，文件系统基本是一个一个处理这些请求的，所以线程再多也快不了多少；右侧文件数上悬停可以看到这次测量用了多久。

打开仓库时是增量测量：每次测完，每个目录自己的修改时间和其中硬链接文件的链接信息会记下来（Windows 上在 `%LOCALAPPDATA%\multibox\measured`，macOS 上在 `~/Library/Application Support/multibox/measured`，一个工作区一个文件，一个月没用到就删掉）。目录里新增、删除或改名了文件，它的修改时间就会变；没变的目录直接沿用记录，一个文件都不用打开。一个 28 万文件的工作区从 6 秒降到 0.3 秒。新建或删除工作区会给其他工作区的文件加上或去掉硬链接，却不改变目录的时间，所以工作区有增减时记录作废、从头测量。在工作区之外给这里的文件建或删硬链接，增量测量看不出来，按 `F5` 从头测量就会更正。
